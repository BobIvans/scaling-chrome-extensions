# Что ещё не определено и не закончено

V5 расширяет определение продукта. Она не меняет код SCE и не объявляет новые
функции установленными. Опора реализации — сохранённый локальный commit V4
`5574ab768b39605d4631651a1e8f2451483344db`; его 381 локальная проверка является
историческим результатом этого изменения, а не проверкой всех целей V5.

## Четыре разных вопроса

| Вопрос | Что требуется для ответа |
| --- | --- |
| Идея сохранена? | Исходная карточка, происхождение, версия и ссылка на каталог |
| Поведение достаточно определено? | Inputs, outputs, owner, state/error/recovery contract, критерий и scope |
| Поведение реализовано? | Актуальный code handler и проверка заявленного критерия |
| Пользователь может применять его? | Доставленная версия, конфигурация, полномочия и receipt на нужном устройстве |

У исходных 164 карточек уже есть проблема, поведение, зависимости, приёмка,
метрика и следующий эксперимент. Это хорошая основа. Однако исходная карточка
обычно не содержит полного wire/storage/runtime-контракта. Решения могут быть
описаны в других документах, поэтому отсутствие поля в карточке не доказывает
отсутствие решения во всём архиве. V5 добавляет ссылки между целями, решениями,
новыми задачами и прежней стратегией вместо автоматического объявления всего
каталога «неопределённым».

Статусы V4: 23 карточки имеют частичное продвижение; две — реализацию в узкой
подтверждённой области; 139 — планируемые или не проверенные в текущей итерации.
Эти числа не означают, что 139 функций точно отсутствуют в любом прежнем коде.
Нужна сверка конкретного handler и приёмки; старый prototype не подтверждает
production/Windows результат.

## Неполностью решённые части

### 1. Поставка Windows desktop

Нужно выбрать production shell и transport к существующим владельцам, способ
установки/обновления, данные профиля, зависимости и поведение при закрытом Chrome.
Обязательный результат: один desktop клиент видит те же источники и задачи;
после перезапуска данные не пропадают. Путь установки проверяется на Windows,
включая отсутствие зависимости от рабочего каталога и понятное восстановление.

Работа в браузерной библиотеке и локальный Native Host уже дают основу, но не
заменяют независимый desktop shell. В архиве остаются прежние прототипы с их
собственными границами. Перед миграцией необходимо инвентаризировать store каждого
реального клиента, не считать одно название «library» доказательством общей базы.

### 2. Полный repo-chunker

Не закончены автоматический проход всех страниц по одной кнопке, единый manifest
всех частей и resolved graph для JS/TS/workspace aliases. Требуется выбрать
контракт graph adapter и границы static/dynamic/ambiguous dependencies.
Large/binary/LFS/submodule/dirty-worktree sources требуют собственных состояний.

Уже есть pinned inventory, bytes, cursor, Python static closure и bounded export.
Новая автоматизация должна продолжать эти операции, а не запускать каждый файл
репозитория. «Учтён весь HEAD», «сохранены все доступные bytes», «включено в пакет»
и «прочитано AI» измеряются отдельно.

### 3. Каталог всей доступной истории

Необходимо зафиксировать schema source/version/extraction/chunk/tag/goal,
границы source identity, conflict rules и миграцию старых хранилищ. Для файлов,
чатов, PDF/Office, медиа и web snapshots нужны отдельные importer contracts.
Вложения/ветви/авторы/цитаты/time spans не должны теряться при нормализации.

Автометки требуют объяснения происхождения, версии классификатора и ручного
override. Retrieval требует проверяемых source ranges, а не только summaries.
Corpus может расти долго; конкретный AI packet остаётся ограниченным и раскрывает
остальные источники через manifest/NEED_CONTEXT. Полнота недоступной истории
не создаётся автоматически из сохранённых пересказов.

### 4. Две указанные вкладки

Нужно выбрать и квалифицировать реальный target identity: account/workspace/chat
для Grok и repo/PR/branch для GitHub. Tab ID после перезапуска не всегда достаточно.
Обязательны draft/upload/send/result наблюдения, пределы документа и recovery
после потерянного ответа. Доступ Grok к GitHub не предполагается: он проверяется
как отдельная возможность выбранной среды.

Для первого canary достаточно маленького тестового TASK с уникальным ID. Проверка
изменения адресата и unknown-send выполняется до включения повторяемого auto-send.
Повторения внутри настроенного scope не требуют одинакового вопроса каждый раз;
расширение действий или смена назначения отражается как новая версия профиля.

### 5. Самообновление и каталог возможностей

Не определён полный release manifest, связь source/assets/build, механизм staging,
миграции данных, переключения активной версии и rollback. Merge, скачивание,
успешный тест и установка — разные события. После установки capability должна
подтвердить действие на устройстве, прежде чем считаться доступной автоматизациям.

Самообновление не должно менять исполняемый компонент посреди его работы.
Выбор updater/launcher и quiescence policy является отдельным решением. Навыки,
зависящие от прежней версии UI/code/policy, требуют избирательной requalification.

### 6. Текст, голос и управление PC

Нужны общий IntentSpec, критические slots, correction/cancel semantics,
registered capability contracts и доверенный источник scope. Source text, AI
ответ и импортированный JSON не становятся полномочием выполнять команды.

Laya и ASR — сменные adapters; их наличие, качество, latency и стоимость пока
не измерены этим ZIP. Keyboard STOP и текстовый путь должны работать независимо
от них. Демонстрация пользователя превращается в навык только после проверки
preconditions/effects/recovery. Универсальная команда «сделай всё» сначала
разрешается в конкретный план и доступные capabilities.

### 7. Длительные и параллельные кампании

Требуются contracts missed-run/catch-up, leases, shared resource identity,
bounded retries, cancellation, budgets и no-progress stop. Настройки Dell 16 ГБ
должны основываться на measurements; текущий production Core остаётся с его
existing serial policy до отдельной квалификации параллелизма.

Можно параллельно готовить независимые immutable данные и исследования.
Состояние одного UI-сеанса, интеграция одного repo и установка одной версии
имеют единственного владельца изменения. Работа в разных вкладках не доказывает
независимость foreground focus или общего desktop ресурса.

### 8. Реальная польза и интеграция исследований

Нужен фиксированный corpus пользовательских задач и отказов. Success ratio,
unknown, retries, human interventions, latency, RAM и полная цена попытки должны
иметь явный знаменатель. Нельзя оценивать результат только количеством PR,
созданных документов или одинаковых заявлений разных моделей.

SCE→Studious integration требует актуальной карты зарегистрированных функций,
data/replay/paper handlers, dataset manifests и qualification receipts. Рыночные
и protocol hypotheses сохраняются как исследования. Каждый новый adapter имеет
свой corpus и условия применимости. Приложение может автоматизировать сбор и
анализ после реализации контракта; существование карточки не запускает бот.

## В каком порядке превращать определения в результат

| Milestone | Видимый выход | Обязательная проверка |
| --- | --- | --- |
| M5-01 | Доставлен текущий task cycle, понятен путь установки | Exact code/build и отдельный Windows receipt |
| M5-02 | Одна кнопка сканирует repo и формирует manifest всех частей | EOF, source drift, interruption, byte roundtrip |
| M5-03 | Полезная локальная библиотека источников и целей | Import/search/tag override/restore на фиксированном corpus |
| M5-04 | Выбраны две вкладки; маленький TASK доставлен и ответ связан | Target drift, upload mismatch, unknown-send recovery |
| M5-05 | Изменение связано с проверенным merge и staged release | Base/final tree, CI и migration evidence |
| M5-06 | Обновление установлено и новая capability наблюдаема | Installed build, canary, rollback на устройстве |
| M5-07 | Текст/голос запускают зарегистрированный план | Slot correction, scope, keyboard STOP, outcome receipt |
| M5-08 | Кампания переживает offline/restart; независимые jobs параллельны | Conflict/lease/budget/catch-up/fault tests |
| M5-09 | Исследовательский workflow возвращает воспроизводимые данные | Dataset/replay/paper evidence и следующий конкретный blocker |
| M5-10 | Долговременный корпус и навыки работают на нужном масштабе | Retrieval utility, backup/restore, selective drift qualification |

M5-02 и discovery для M5-04 могут идти параллельно. M5-03 не требует уже
подключённого Grok. Text accessibility начинается в первых UI, а голосовой
adapter не блокирует подготовку контекста. M5-09 использует подтверждённые
registered research functions, не зависит от обещания всех будущих стратегий.

## Где находится дальнейшая детализация

* `goals/GOAL_REGISTER.json` — 28 проверяемых outcome groups, покрывающих все
  164 унаследованные карточки. Они могут пересекаться.
* `audit/DECISION_REGISTER.json` — конкретные оставшиеся operational decisions:
  варианты, рекомендованная отправная точка, эксперимент и условие выбора.
* `actions/TASKS_ACTION5.json` — новые задачи, уточняющие прежний backlog.
* `catalogs/FEATURE_DEFINITION_AUDIT.json` — связь каждой карточки с целями,
  решениями, задачами и прежним evidence scope.
* `catalogs/ALL_TASKS_V5.json` — общий граф задач V3–V5.

Новые варианты и пороги остаются предложениями до измерения. Вопросы из реестра
решений не требуют немедленного ответа пользователя: сначала выполняется
дешёвый проверяемый experiment и готовится конкретный вариант для выбора.
