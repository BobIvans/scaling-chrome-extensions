G3-010 — Создавать следующий R&D brief по новым данным
- У задачи есть gap, новая evidence delta и критерий результата.
- Повтор без новых данных не создаёт бесконечную кампанию; бюджет/stop condition соблюдены.
UI3-015 — Распараллелить подготовку и проверку с одним UI-писателем
- Два worker не изменяют один composer одновременно; разные чаты не обходят desktop-session mutex.
- Конфликт по файлам/результатам становится интеграционной задачей.
PAR3-002 — Неизменяемые входы и общий manifest кампании
- Каждый узел ссылается на snapshot ID, commit и хеш входного manifest.
- Полнота raw capture, unresolved graph edges и omissions представлены отдельно.
- Два работника получают один и тот же зафиксированный вход, даже если current main изменился.
PAR3-004 — Каноническая идентичность ресурсов Windows
- Case aliases, separator aliases, UNC, volume, symlink и junction проходят реальные Windows fixtures.
- Read/write scopes привязаны к физической идентичности или отмечены unknown.
- Clipboard, window/chat и Git metadata имеют устойчивые resource IDs.
PAR3-006 — Граф конфликтов исполнения и будущей интеграции
- Read/read одного immutable snapshot допускается параллельно; write/read и write/write пересечения сериализуются.
- execution_write_set и integration_write_set независимы: разные worktree могут готовить будущий конфликтующий patch.
- Unknown runtime effects получают эксклюзивное выполнение; поздний фактический diff заменяет предположение о merge overlap.
PAR3-007 — Admission control для CPU, RAM, UI и провайдеров
- Начальный профиль Dell отмечен proposal; каждое решение сохраняет свободную и зарезервированную ёмкость.
- Нельзя получить lease, если превышены worker, memory estimate, heavy, UI или provider slots.
- Базовые UI/STOP не зависят от свободного рабочего слота.
PAR3-008 — Атомарные leases, fencing и единственный DB writer
- Выдача lease и resource reservation атомарны в существующем store.
- Каждая попытка получает новый fencing token и checkpoint references.
- Истёкший worker не подтверждает success и не перезаписывает новую ревизию.
PAR3-011 — Общий кеш доказательств и безопасное переиспользование
- Ключ включает source snapshot, selected input hashes, goal, parser/rules и capability version.
- Raw данные не скачиваются повторно для независимых потребителей одного ключа без необходимости.
- Кеш подтверждает hashes, completeness и freshness; derived claims остаются атрибутированы.
PAR3-014 — Резервирование бюджета и ограничения backlog
- Перед платным эффектом резервируются configured верхние оценки запросов, входа/выхода и стоимости.
- Unknown price/quota не считается нулём; UI и API budgets не смешиваются.
- Одинаковые не начатые события coalesce; stale jobs становятся superseded с сохранением исходных намерений.
PAR3-016 — Resume с верификацией входов и остатка DAG
- После restart проверены hashes, SHA, grants, capability version и неопределённые эффекты.
- Успешные подтверждённые узлы переиспользуются, остальной DAG перепланируется.
- Истёкшие reservations освобождены только после определения судьбы эффекта.
PAR3-019 — Планирование по доступным возможностям и aging
- Недоступная версия/доступ/квота блокирует только затронутый узел с точной причиной.
- Приоритет задаёт доступность/STOP, reconciliation, interactive, background; aging уменьшает голодание background.
- Laya выбирает только разрешённые candidate IDs и может abstain; она не меняет grants или budgets.
PAR3-020 — Журнал решений и представление зависимостей
- Каждый transition содержит campaign/node/attempt/revision, hashes, evidence и причину.
- UI объясняет ready/running/waiting/blocked/unknown и владельца конфликтного ресурса.
- Projection перестраивается из событий; метки поиска сохраняют provenance и ручные исправления.
PAR3-021 — Доступный контроль очереди; голосовой parity как отдельное расширение
- Queue, причины ожидания, локальный STOP, исправление текстовой цели и resume доступны клавиатурой и выбранным screen reader.

PAR3-023 — Инвалидация устаревших исследовательских ветвей

EVO3-021 — Следующий R&D документ из доказанных gaps

- Brief строится до release/install/usable: достаточно текущего ledger с manual checkpoint или verified evidence. Данные установленного устройства добавляются при наличии; их отсутствие отражается как gap.

- Подготовка parallel proposals доступна до install/usable и не зависит от готового следующего brief; если worker требует внешнего эффекта, применяется отдельный activation gate.
