ЭКСПЕРИМЕНТЫ СКОРОСТИ И ДОСТУПНОСТИ — ПРОЕКТ, НЕ РЕЗУЛЬТАТЫ
2026-10-03. Все измерения NOT_RUN. Рекомендации ниже — инженерные гипотезы, численные пороги выбираются после baseline на конкретном Dell.

Метрика главная: время от конца произнесённой команды до проверенного полезного результата. Дополнительно: время до ACK, первого найденного свидетельства, готового плана, начала/конца действия; доля верно выполненных задач; стоимость; число исправлений; stop latency. Измерять p50/p95, cold/warm, CPU/GPU/RAM и влияние параллельных задач на foreground responsiveness.

EXP-P01: локальный ASR против выбранного облачного ASR.
Корпус пользователя: русский, English, смешанные Git/Web3 имена, адреса, цифры, отрицания; тихая комната, шум, разные микрофоны. Идентичные аудиозаписи и human transcript. Считать WER/CER, но главное — intent/slot error и опасная инверсия отрицаний. Local large model может быть медленнее малого CPU-моделя: сначала измерить оборудование. Чувствительные аудио по умолчанию остаются локально.

EXP-P02: routes rules → Laya → larger model.
Заморозить held-out 100+ типовых целей и неизвестных запросов пользователя, сбалансировать read/write и языки. Сравнить rules-only, local Laya, provider-only, гибрид с abstain. Метрики: верный route, неизвестный ошибочно признан известным, tool/argument error, latency, доля escalations. Нельзя выбирать порог Laya по той же тестовой выборке, которой затем заявляется качество.

EXP-P03: предварительный retrieval по стабильным ASR-сегментам.
Запускать только read-only поиск до окончания речи; отменять stale search при исправлении транскрипта. Сравнить first evidence и общую latency с retrieval после commit. Ошибочное выполнение изменяющей команды до commit — запрещённый исход; этот опыт не включает execution speculation.

EXP-P04: API/CLI → UI Automation → vision click.
Одинаковые доступные действия на Windows: открыть источник, найти запись, экспортировать пакет, запустить известный тест. Сравнить latency и reliability. API/CLI и семантические UI handles предпочтительны; screenshots/мышь нужны для приложений без доступного интерфейса. Изменение окна/масштаба/фокуса должно входить в негативные fixtures.

EXP-P05: context cache и delta re-index.
Базовый путь каждый раз заново сканирует весь репозиторий; кандидат использует content hash и инвалидацию зависимости. Проверить, что изменение одной строки обновляет нужные chunks/derived labels/retrieval и сохраняет старую версию с provenance. Считать bytes read, cache hit, stale evidence rate. Экономить повторную обработку, а не удалять неудобные документы из coverage.

EXP-P06: параллельный DAG и лимиты ресурсов.
Сравнить serial/2/4 workers на read-only retrieval, статике и независимых тестах. Динамические CPU/RAM/GPU/network tokens дают backpressure; очередь остаётся полной. Для foreground input строго один владелец; для каждого worktree один writer; для signer один nonce owner. Считать critical path, waiting locks, starvation и responsiveness. Больше workers не всегда быстрее.

EXP-P07: один готовый recipe вместо цепочки мелких model calls.
«Собери контекст и проверь regression» разворачивается в локальную версионированную recipe. Модель видит результат и evidence, а не выбирает каждый list/read/copy. Сравнить model roundtrips, стоимость и error rate. Новый неизвестный процесс всё ещё требует планирования и схемы; cached recipe должен быть привязан к версии handlers и исходным предположениям.

EXP-P08: устойчивость self-update.
Fault injection: неверная подпись; правильная подпись чужого repository/workflow; stale commit; timeout на download; нехватка диска; interrupt в migration; несовместимый schema; healthcheck fail; новая запись пользователя после старта update; новый scope. Должен оставаться рабочий launcher, проверяемая предыдущая версия и сохранённая библиотека. Отдельно проверить отсутствие ложного «обновлено».

EXP-P09: accessibility task completion.
Участники с различными способами управления проходят сценарии голосом, клавиатурой, screen reader и комбинированно. UI имеет accessible names, status announcements, текстовый trace, крупные targets, настраиваемые таймауты, альтернативу press-and-hold. Критерии — успешное выполнение и возможность восстановиться после ошибки; не обещать универсальность для всех состояний по тесту одного человека.

Полезные направления инновации для нашего приложения:
1) Цель как исполняемый документ: текст, evidence, план, grants, receipts и проверяемый итог связаны ID.
2) Объяснимое предложение автоматизации: повторяющаяся последовательность → recipe candidate → replay → измеренный выигрыш.
3) Локальная память решений с конфликтами и датами: текущая цель не теряется за старым советом модели.
4) Возможности обновляются независимо от доверия: код, credentials, scopes и доказательство работоспособности имеют разные статусы.
5) Быстрый локальный путь для известных команд и background R&D для новых; результаты превращаются в новую versioned recipe после теста.

Это предложения для экспериментов, не подтверждённые новые научные результаты и не заявка на первенство.
