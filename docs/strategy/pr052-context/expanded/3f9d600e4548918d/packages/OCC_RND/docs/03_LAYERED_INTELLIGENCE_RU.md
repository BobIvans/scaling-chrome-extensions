# Как программировать layered intelligence для автоматизации

Ниже — наш предлагаемый проект. «System 1», «System 2» и «слои интеллекта» обозначают инженерные роли; это не обещание AGI, безошибочного агента или выполнения любой задачи.

## Что изменилось в доступных инструментах

Jev описан разработчиком как модель структурированных решений; пример LangChain показывает её внутри отдельного harness. Объявление датировано 15 сентября 2026, пример — 17 сентября. Практический вывод: быстрый выбор следующего действия не заменяет инструменты, durable state и проверки результата. [S01, S02]

Laya — локальный кандидат для той же узкой роли. Multilingual-вариант по умолчанию ограничивает вход 1 024 токенами; для большего входа явно настраивается до 8 192. Карточка предупреждает о слабом zero-shot typed-decisions, необходимости калибровки и бесполезном `action.act_probability`. Поэтому это advisory-router, не механизм выдачи прав. GPU latency разработчика не является измерением на Dell. [S03]

## Рабочая последовательность

1. **Observation:** получаем реальный файл/API/UIA/DOM state и provenance, а не только пересказ пользователя.
2. **Input normalization:** финализируем ASR, сохраняем оригинал и альтернативы, разрешаем опечатки имён из локального registry.
3. **Deterministic fast path:** точные команды и уже зарегистрированные навыки обрабатываются без LLM.
4. **Typed routing:** небольшой классификатор выбирает семейство задачи, missing-data category и необходимость эскалации. Его ответ остаётся предположением.
5. **Context compilation:** для выбранного семейства собираются актуальные источники, версии, предыдущие неудачные попытки и ограничения.
6. **Planning:** LLM составляет DAG из доступных capabilities. Неизвестный capability становится proposal на разработку, не придуманной командой.
7. **Admission:** JSON Schema + эффектные типы + policy + права на источник + budget + exact SHA + risk проверяются обычным кодом.
8. **Execution:** API/CLI/UIA/DOM adapter выполняет короткий шаг и возвращает наблюдаемое состояние.
9. **Verification:** отдельный oracle проверяет postcondition. Exit 0 или текст «готово» не достаточны для всех задач.
10. **Learning:** trace превращается в пример для offline-обучения/нового навыка после независимого review и holdout-теста.

Слой добавляется только когда улучшает измеряемую задачу. Не нужно запускать десять моделей на каждую короткую команду.

## Типизированные эффекты вместо «модель уверена»

`ReadLocal`, `ReadNetwork`, `WriteWorkspace`, `ExecuteReviewedCode`, `PublishExternal`, `SpendMoney`, `SignTransaction` — разные эффекты. Планировщик не может преобразовать read-only навык в подписанта. Эффекты объединяются по всему DAG до исполнения; новый effect требует отдельного согласования. Текст источника всегда DATA, а не новая policy.

Условия возвращают `TRUE / FALSE / UNKNOWN / NOT_RUN / STALE / BLOCKED`. Например, `repo_sha_matches=TRUE` проверяется Git, `code_is_correct=UNKNOWN` до теста, `profitable=NOT_RUN` до кампании с релевантными измерениями. Вероятность маршрутизатора не должна переименовываться в `verified=true`.

## Иерархия исполнения

Для существующей задачи сначала пробуем официальный API, затем фиксированный CLI, UIA/COM для Windows или DOM для браузера; screenshot/model-based clicks — последний вариант, когда семантический интерфейс отсутствует. Это проектный приоритет, не универсальная гарантия. Windows API, FlaUI/pywinauto, Playwright MCP дают разные адаптеры для разных поверхностей. [S10, S12–S14]

## Новые R&D-гипотезы

**Intent compiler:** natural language → effect-typed intermediate representation → executable DAG. Компилятор отвергает несуществующие capabilities и требует evidence для критических зависимостей.

**Evidence debt ledger:** каждое «не знаю» становится задачей получить конкретное доказательство. Очередь ранжируется по ожидаемому уменьшению неопределённости, цене, правам и вероятности изменить решение.

**Skill distillation:** успешный trace сначала повторяется без модели; только повторяемый участок компилируется в фиксированный adapter. Модель возвращается лишь на неоднозначные развилки.

**Counterfactual replay:** сравниваем «сделать A», «сделать B», «собрать данные», «ничего» на сохранённом состоянии, не на реальном кошельке/продуктивном ПК.

**Minimal repair:** при UI drift исправляем локатор и его проверку, а не позволяем агенту заново свободно бродить по рабочему столу.

**Budgeted disagreement:** второй critic вызывается только когда потенциальная ошибка дороже проверки; два согласных LLM всё равно не создают фактического подтверждения.

## Скорость считать от результата

Предлагаемая метрика: `verified useful completions / wall-clock hour / euro`, вместе с долей вредных действий и исправлений пользователя. Время всей операции включает ASR endpointing, ожидание очереди, чтение состояния, retrieval, планирование, проверки, инструмент и повторы. Ускорение одного classifier не даёт автоматически такого же ускорения workflow.

В первую очередь измерить повторное использование state, dedup запросов, ready-to-run profiles, маленькие диффы, заранее прогретый один нужный модельный процесс и независимые read-only jobs. Затем сравнивать Laya/Jev/маленький LLM на одной замороженной выборке.
