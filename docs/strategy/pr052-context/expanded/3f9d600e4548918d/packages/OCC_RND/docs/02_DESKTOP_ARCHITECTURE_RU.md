# Windows-приложение вместо обязательного Chrome extension

## Предлагаемое решение

Один desktop-shell, существующее Python-ядро SCE и один canonical store. Chrome-extension сохраняется только как необязательный способ захвата отдельных страниц; отсутствие extension не должно блокировать импорт файлов, Git, библиотеку, API, terminal jobs или qualification.

Первый вертикальный срез: выбрать репозиторий → получить immutable snapshot → построить пути/поиск/каталог → сформировать полный context export → открыть конкретный символ в VS Code → запустить одну заранее проверенную qualification-команду → вернуть receipt в библиотеку. Голос подключается к этому же typed API, не образует второй механизм исполнения.

## Границы модулей

| Модуль | Ответственность | Не имеет права |
|---|---|---|
| Desktop UI | Файлы, поиск, задачи, previews, согласия, состояние очереди | Самостоятельно подписывать транзакции/менять полномочия |
| Ingestion adapters | Файлы, ChatGPT/Telegram export, Git/API, аудио | Исполнять инструкции из прочитанного документа |
| Canonical store | Original blobs, versions, paths, refs, ACL/privacy, journal | Считать summary заменой оригинала |
| Context compiler | Выбор доказательств, частей, gaps, token accounting | Прятать неотправленные части под словом «полный» |
| Capability registry | Реальные команды, эффекты, pre/postconditions, owners | Автоматически разрешать всё найденное AST-сканером |
| Planner/router | Предложение typed intent/плана | Определять свой executable, cwd, signer, бюджет |
| Executor | Только одобренные profiles; leases, cancellation, receipts | Считать текст LLM авторитетной политикой |
| Independent verifier | Проверка реального изменения состояния | Подменять результат повторным мнением той же модели |

Это проект архитектуры, а не утверждение, что перечисленные слои уже реализованы в репозитории.

## UI, ориентированный на реальные операции

Левая панель: Sources, Library, Repositories, Runs, Skills, Research, Privacy. Центральная область: список без потолка документов, виртуализированные строки и пагинация. Правая: preview исходника, SHA/время/путь, origin, выбранные spans, текущие права. Внизу: job log с понятными стадиями и аварийной остановкой.

Library: папки, теги, backlinks, сохранённые queries, коллекции и attachments. Repository: дерево всех путей, функции/imports, snapshot diff, «почему этот файл включён», «что ещё не проверено». Runs: proposed/running/blocked/failed/verified; не один зелёный флаг на всё. Skills: декларативные входы/выходы/права/тесты/версии. Research: гипотеза, baseline, датасет, измерения, отрицательный результат и следующий запрос данных.

## Выбор оболочки

На старте сохранить Python backend и сделать тонкую Windows UI. Приложенный Tk front-end — только запускаемый архивный прототип, не конечная рекомендация дизайна и не сертифицированная accessibility-среда. Для production отдельно сравнить native .NET UI + UIA adapter и доступный webview-shell; измерять установку, клавиатуру, screen-reader, idle RAM, crash recovery, signing/update story.

Не встраивать целый IDE в первом срезе. Внешний VS Code можно связать с evidence path/line через его CLI; это уменьшает объём собственной разработки. [S29] Предлагаемые действия: `open_file`, `open_diff`, `reveal_repo`, `show_run_log`; каждый с фиксированным adapter и проверенным root.

## Терминал — это две разные функции

Интерактивный терминал пользователя можно показать отдельно, с явным индикатором что ввод делает человек. Автоматические jobs должны идти через command registry, а не через строку терминала. Команда имеет id, executable, argv-template, cwd, переменные окружения, таймаут, сеть, область записи, ожидаемый exit/domain verdict и output contract.

Git worktree отделяет изменения исходников, но не защищает ПК от исполняемого кода. Неизвестные тесты/пакеты требуют отдельной sandbox/VM/container-среды с минимальными правами; её наличие надо доказать на конкретном Windows edition и окружении.
