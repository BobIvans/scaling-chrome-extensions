# Voice → automation и доступность: проект и проверка

Это функциональный проект для разных способов взаимодействия, не медицинское обещание и не предположение о диагнозе пользователя.

## Один intent API, несколько входов

Голос, обычный текст, клавиатура, переключатель, доступные кнопки и при необходимости стороннее assistive device должны вызывать одни и те же typed capabilities. Только голосовой интерфейс может оказаться менее доступным для человека с трудностями речи, шумной средой или усталостью.

Команда «собери контекст repo и подготовь проверку» превращается в отображаемый план: какой источник, какой commit, куда сохранить, будет ли сеть, будет ли исполнение кода. Интерфейс читает этот план вслух по запросу и даёт альтернативу подтверждению мышью. Финансовые/публикуемые действия не включаются через распознанное фоновое «да».

## Предлагаемый голосовой конвейер

Capture с явным индикатором → VAD/endpointing → ASR → сохранение оригинального transcript и альтернатив → исправление локальных entity names → typed intent → preview → policy → execute → state verification → короткая обратная связь.

Частичный ASR никогда не исполняет необратимый шаг. «Не запускай», «отмени», «нет» и исправление чисел рассматриваются как отдельные adversarial cases. TTS собственного агента не должен повторно включать его команды. Stop shortcut/кнопка не должны зависеть от ответа LLM или очереди ASR.

Для начальной проверки сравнить faster-whisper и Qwen3-ASR-0.6B, не утверждая заранее победителя на CPU. [S18, S19] Использовать пользовательские записи с разрешения: русская речь, английские имена API, код/тикеры, паузы, самокоррекция, шум. Считать не только WER, но и ошибку intent/слотов: неверная сумма или слово «live» важнее опечатки в обычном существительном.

## Windows-контроль

Предпочитать семантические control properties и стабильные locators. UIA — официальный слой Windows; FlaUI и pywinauto — кандидаты на adapter. NVDA — один из целевых screen-reader для реального acceptance-теста. [S12–S15] Наличие UIA API не доказывает, что конкретное приложение экспонирует все нужные элементы.

## Acceptance matrix, которую ещё предстоит выполнить

- Полное прохождение основной задачи без мыши, с видимым focus и логичным tab order.
- Чтение label/state/error screen-reader; отсутствие ловушек фокуса и обновлений, постоянно перебивающих чтение.
- Прерывание задачи при зависшей модели, медленной сети и занятой очереди.
- Возврат к предыдущему шагу без двойного исполнения действия.
- Возможность исправить intent/параметр текстом, не повторяя длинную голосовую команду.
- Работа после sleep/resume, смены микрофона, отказа аудио и неожиданного всплывающего окна.
- Раздельные согласия на запись аудио, хранение, облачную транскрипцию и передачу контекста.

Все эти тесты имеют статус NOT_RUN на твоём Dell в данном пакете. Скриншот красиво работающего приложения не заменяет эти проверки.

## Исследовательские идеи

«Conversational undo» — перед записью операции сохранять обратимое состояние и показывать, что именно можно отменить. «Intent echo» — произносить только критические параметры, снижая усталость от длинных подтверждений. «Ambiguity heatmap» — подсвечивать сомнительный слот и спрашивать только его. «Demonstrate once» — запись разрешённого действия пользователя → replay в копии данных → reusable skill с postcondition. Последнее направление стоит сравнить с подходом OpenAdapt, не принимая демонстрацию за доказательство надёжности. [S06]
