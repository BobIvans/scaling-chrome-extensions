ПРАВИЛА ПРОДОЛЖЕНИЯ И ОБНОВЛЕНИЯ ПАКЕТА

1. Читать актуальный корневой handoff, затем оригиналы релевантных источников.
   Legacy START/REQUEST внутри packages имеют историческую область действия.
2. Слова пользователя сохранять без исправления. Интерпретацию хранить отдельно.
   Каждая новая идея содержит source ID/span; proposal ассистента имеет author.
3. Не удалять отвергнутые/отложенные идеи: ставить status и superseded_by/reason.
4. Перед code change прочитать текущий repo и инструкции; исторический SHA не
   превращается в current HEAD. Связать старый backlog с найденными owners.
5. Для результатов хранить inputs/revisions/commands/logs/verifier и NOT_RUN,
   если исполнения не было. Сохранение JSON не означает исполнение workflow.
6. Расширять capabilities по одному проверяемому вертикальному сценарию.
7. Хранить новые источники целиком; для binaries — оригинал и статус извлечения.
   Не заменять архив длинным prompt. Полный TXT и выбранный context pack сосуществуют.
8. После каждой сессии обновить: what changed, decisions, next small step,
   source gaps, function/workflow statuses, проверяемый manifest.

ПРОВЕРКА ПОНИМАНИЯ НОВЫМ ЧАТОМ
• Каков ближайший приоритет пользователя? (M002: агрегировать и передать контекст AI.)
• Что означает отсутствие потолка 20 документов? (Полный источник сохраняется;
  очереди и части не скрывают остаток.)
• Что изменено в подходе к параллельности? (Много producers; locks по общим ресурсам.)
• Какие функции уже работали, а какие SPEC? (Смотреть исходные statuses и evidence;
  не выводить это из количества карточек.)
• Какие данные отсутствуют? (SOURCE_COVERAGE и связанные coverage-файлы.)
• Какое следующее изменение? (N01–N03, с актуальным repo и существующими owners.)
