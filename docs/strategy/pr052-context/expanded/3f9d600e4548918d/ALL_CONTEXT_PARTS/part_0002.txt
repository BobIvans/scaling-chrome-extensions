МЕТКИ ДЛЯ ЛЮБОГО ФРАГМЕНТА: СХЕМА ДЛЯ ДАЛЬНЕЙШЕЙ РАЗРАБОТКИ

Слои записи:
• original: байты/объект источника, неизменяемый идентификатор, SHA-256;
• source_version: источник, revision, path/URL, время capture и source time;
• span: file offsets, message ID, page, timestamp audio/video или symbol;
• interpretation: метки, связи и выводы с авторством, версиями и обоснованием;
• outcome: выполненные действия и независимые evidence receipts.

Базовые измерения меток:
1. source_kind: repo/chat/document/web/audio/video/image/terminal/observation.
2. author_role: user/assistant/tool/external/unknown; speaker и source identity.
3. information_kind: requirement/idea/decision/question/task/fact/hypothesis/
   code/test/error/result/constraint/proposal. Несколько меток допустимы.
4. scope: project, repo, path, symbol, goal, entity, topic, workflow/capability.
5. chronology: created/captured/valid_from/valid_to/revision/supersedes.
6. evidence: asserted/suggested/verified/disputed/unknown; отдельный link на
   критерий и результат TRUE/FALSE/UNKNOWN/NOT_RUN. Уверенность модели не proof.
7. lifecycle: inbox/to_review/accepted/planned/in_progress/blocked/done/
   deprecated; текущий статус хранится как view истории событий.
8. access: local/private/selected_provider/exportable; scope конкретного источника.
9. provenance: exact span, parent links, extractor/model/version, изменивший метку.
10. relevance: цель и объяснение связи; urgency/priority — отдельно от truth.
11. quality: parse/coverage/freshness/conflict/missing-dependency состояния.
12. action: proposed capability, inputs, required evidence, expected outcome.

Теги могут быть unknown, многозначными или спорными. Не подменять отсутствующее
значение выдуманным. AI предлагает метки; исходная фраза сохраняется и пользователь
может исправлять классификацию. Хранить отрицание, временные условия и автора.

Связи:

ОБЩАЯ СТРАТЕГИЯ

Создаём личное локальное рабочее пространство на Dell Windows 11. Оно хранит
оригиналы файлов, репозитории, разговоры, документы, записи и результаты; даёт
поиск, страницы, теги, связи и представления; собирает контекст задачи для AI;
постепенно добавляет проверяемые действия через голос, текст и кнопки целей.
BobIvans/scaling-chrome-extensions — существующая основа, а desktop должен
работать без обязательной зависимости от Chrome extension. Flashloan/Studious
Pancake — важный первый прикладной проект этой системы.

БЛИЖАЙШАЯ ПОЛЬЗА
Импортировать весь выбранный repo ZIP/папку, сохранить пути и байты, получить
понятный полный TXT и связанные части, перенести их в AI, получить изменение,
сохранить результат и продолжить в следующем чате. Именно этот цикл проверять
раньше обещания «автоматизировать что угодно».

ДОЛГОСРОЧНЫЙ ЦИКЛ
Голос/текст/кнопка цели → транскрипт и intent → нужный контекст из библиотеки →
описание задачи и критериев → существующий workflow либо предложение нового →
код/CLI/API/браузер/desktop исполнение → проверка фактического результата →
запись evidence, цели и следующего шага → повторное использование удачного навыка.
Для новой функции: context document → выбранный AI/coder → отдельная рабочая
ветка → patch и тесты → review/merge по конкретному заданию → release → проверка
обновления → локальное применение и возможность возврата прошлой версии.

ЧЕТЫРЕ РАЗНЫЕ ПОЛНОТЫ
1. Сохранность источников: байты, пути, идентичность и версии присутствуют.
2. Извлечение: какие форматы и участки преобразованы в текст/структуру.
3. Осмысление: какие идеи и зависимости отмечены, что осталось неизвестным.
4. Исполнение: какие действия и проверки реально выполнены на каких входах.
Полный ZIP не равен полному prompt, прочитанному моделью. Полный prompt не равен
доказанной правильности кода. Хранение оригинала не означает распознавание каждого
изображения, PDF, аудио или бинарного файла.

«БЕЗ ПРОИЗВОЛЬНЫХ ЛИМИТОВ»
Не отбрасывать документы после двадцатого, хвост большого архива или длинного файла.
Хранить весь выбранный источник; обработку делать потоково с checkpoint, очередями,
возобновлением и явным статусом RAW_ONLY/ERROR/PENDING. При нехватке диска, памяти
или бюджета сообщать о причине и сохранять место продолжения. Ограничение размера
пакета модели задаёт число частей и проходов, а не потерю оригинальных данных.
Полный review ведёт журнал всех spans/частей; summary и embeddings — производные.

ДАННЫЕ И ИХ МЕТКИ
Источник → version/revision → raw object → фрагмент/span → утверждение/идея/задача →
связь с целью → код/тест/доказательство. Отделять user requirement от assistant
proposal, факт от гипотезы, старое решение от superseded, PASS от NOT_RUN.
Метки должны объясняться и исправляться. Исходная фраза и история исправлений
остаются доступными. Подробности: LABELING_ANY_DATA_RU.txt и прежние labeling schemas.

РЕАЛЬНАЯ РОЛЬ LAYA И СЛОЁВ ИНТЕЛЛЕКТА
Сохранённые исследования рассматривают небольшие модели решений/классификации
как один компонент. Архитектура отдельно содержит ASR, parser, retrieval, planner,
registry возможностей, executors и verifier. Конкретный Laya backend, версия,

Первый маршрут можно строить на правилах и существующих командах, затем сравнить
локальную модель с baseline на одинаковых задачах. Необоснованное решение может
возвращать UNKNOWN/NEED_CONTEXT, а не выдуманное успешное выполнение.

ПАРАЛЛЕЛЬНОСТЬ
Последнее сохранённое уточнение пользователя разрешает рассматривать несколько
стратегий записи одновременно. Независимые producers добавляют observations,
сборщики читают свои источники, code workers готовят изменения в разных worktrees,
независимые проверки и paper/replay кампании могут идти параллельно.
Координировать нужно конкретный общий изменяемый ресурс: одну ветку, файл, запись,
внешнюю операцию или активное окно. Общий глобальный «один writer на всё» мешает
цели и не является требованием пользователя. Подробнее: DECISIONS_AND_TENSIONS_RU.txt.

WEB3 КАК ПЕРВАЯ ПРОВЕРЯЕМАЯ ВЕРТИКАЛЬ
Найти доступную актуальную версию bot repo; собрать inventory, команды запуска,
тесты, qualification entrypoints и source lines. Первый законченный сценарий:
«собери контекст блокера и выполни зарегистрированную локальную проверку» →
план → logs/testcases → TRUE/FALSE/UNKNOWN/NOT_RUN → документ для дальнейшего AI.
Далее: reproducible build, smells, unit/fuzz/invariants, pinned replay/fork,
сбор данных, provider comparison, freshness, fees, liquidity, repayment,
paper observation, stop/recovery и release evidence. Синтетический PASS остаётся
синтетическим. Готовность к live — отдельное решение, не следствие упаковки ZIP.

КАК ИЗМЕРЯТЬ ПРОГРЕСС
Полнота paths/bytes/spans, доля пропущенных обязательных источников, корректность
тегов и авторства, воспроизводимость patch/test, p50/p95 time-to-verified,
стоимость на проверенную задачу, latency остановки, восстановление после сбоя,
ручные исправления и достижение конкретных ежедневных целей.

не удаляя их при смене ближайшего приоритета.

Runtime не менялся. Архивная проверка не заменяет будущую проверку приложения.

ПЕРВАЯ СЛЕДУЮЩАЯ РАБОЧАЯ СЕССИЯ
N01. Прочитать handoff и проверить актуальные owners/HEAD существующих репозиториев.
     Найти реальный выбранный repo ZIP/checkout и точку входа библиотеки.
     Прежние SHAs в evidence — исторические; не считать их автоматически текущими.
     Результат: короткая карта owners и один выбранный небольшой diff.
     Связи: SCE D01–D04; OCC DESK-01/02; VOICE CTX-CAP-01/CTX-PAR-01.

N02. Подключить raw-first импорт и полный экспорт к существующему store SCE.
     Один владелец состояния и очереди, desktop как клиент. Не вводить вторую
     независимую библиотеку только ради нового окна.
     Проверка: >20 документов, крупный архив, длинные пути, повторяющиеся paths,
     binary/raw-only, ошибка parser, restart и повторный импорт; сверка bytes/hashes.
     Результат: полный manifest + originals + TXT parts + coverage/error ledger.
     Связи: D02/D03/D04; CTX-01; LABEL-02/03/12/13.

N03. Сделать завершённый handoff в новый AI-чат и импорт ответа обратно.
     Repo map, символы, зависимости, tests/docs/history, WHY_THIS_PACKET,
     исходные spans, required slots, omitted/pending, multipart review ledger.
     Проверка: потерянная критичная зависимость видна; размер prompt не обрезает
     оригинал; ответ привязан к версии источников и нужной цели.
     Связи: D05/D08/D09/D10; CTX-10/15; CTX-CAP-02.

N04. Довести один desktop-поток на Dell Windows 11.
     Импорт → библиотека → выбранная цель → экспорт → статус. Проверить обычный
     запуск, Unicode paths, отсутствие обязательного Chrome, ошибки и отмену.
     Добавить переход в VS Code к path/line и чтение результатов команды.
     Выбор новой UI-платформы оставить отдельным экспериментом, если текущая
     основа не удовлетворит измеримым потребностям.
     Связи: D01/UI-01; OCC desktop; T04.

СЛЕДУЮЩИЙ ЭТАП ПОСЛЕ ПЕРВОГО ЦИКЛА
N05. Подключить теги, цели и provenance к реальной библиотеке.
     Импортировать выбранные экспорты ChatGPT/Grok/Telegram/Docs. Сохранить роли,
     ветки, revisions и все оригинальные сообщения. UI показывает предложенную
     метку, цитату и возможность исправить её. Daily plan строится по open goals.
     Связи: D06/D07; LABEL-01–18; CTX-02/04/05/08/09.

N06. Реализовать одну bot qualification-команду через зарегистрированный adapter.
     Найти существующий entrypoint и настоящие test commands в текущем bot repo;
     использовать отдельную рабочую директорию и собрать логи, testcases, exit
     status, версии входов и postcondition. Показать blockers и UNKNOWN.
     Проверить и положительный, и отрицательный результат, stale evidence.
     Связи: CTX-PAR-05; W3-F01–13; SMELL-01–10; OCC command candidates.

N07. Добавить голос к тому же typed intent/action пути.
     Push-to-talk → RU/EN transcript → исправление → intent → понятный preview →
     тот же проверенный сценарий. Отдельный stop/cancel. Проверить доступность,
     имена repo, отрицания, шум, прерывание и поведение после restart на Dell.
     Laya сначала сравнивается как advisory router с deterministic baseline.
     Связи: CTX-PAR-06; LVF05–09/21; PIPE-01/02/17.

N08. Ввести многопоточный сбор и измерить выгодную параллельность.
     Несколько producers → immutable observations → reconciliation/views.
     Независимые worktrees и tests; общий ресурс имеет конкретного владельца.
     Сравнить serial, eager-parallel и delayed-hedge при одинаковом бюджете.
     Проверить late arrivals, дубли, source drift, отмену losers и foreground user.
     Связи: CTX-CAP-01; CTX-PAR-03/04; RND-43–54; PIPE-06/18.

N09. Закрыть один coding roundtrip.
     Context pack → выбранный provider (Grok/OpenAI/другой) → отдельный worktree →
     patch → независимые проверки → reviewable diff/PR → evidence в библиотеку.
     Сохранить происхождение исходной цели, изменения и результатов.
     Связи: CTX-PAR-07; PIPE-04/08/09/10; FUT-016–018.

ПОЗЖЕ: СОХРАНИТЬ В BACKLOG, НЕ СЧИТАТЬ ЗАБЫТЫМ
N10. GitHub release watcher, capability diff, staged updater, миграции и rollback.
     Сначала проверить обновление/возврат на копии состояния. Новая capability
     и новый доступ — отдельные элементы конфигурации; архив не выдаёт их сам.
N11. Расширить квалификацию до набора реальных web3 campaigns и параллельного
     replay/paper портфеля; свежесть данных, полные комиссии, provider disagreement,
     faults, stop и reproducibility. Live — отдельный последующий этап.
N12. Добавлять коннекторы, browser/Windows UIA, MCP library tools, adaptive UI,
     мультимодальность, personal memory, обучение тегов, skill factory и продуктовые
     эксперименты. Для каждого — один критерий пользы и измеримый результат.

КОНКРЕТНЫЙ ПЕРВЫЙ РЕЗУЛЬТАТ, КОТОРЫЙ НУЖЕН
На выбранном repo ZIP >20 файлов: все entries учтены; полные пути и raw сохранены;
можно собрать весь текст или пакет цели; видно, что обработано/не обработано;
новый чат понимает следующий patch; его результат возвращается в библиотеку.
Именно этот сценарий завершать, прежде чем расширять число одновременно строящихся
интеграций. Все дальние идеи уже сохранены и могут быть подняты позже.
